# AI-SCOUT 설계

> 상태: **설계안** (2026-11-09). 개인 하네스의 주간 스카우트(2026-11-04~)를 누구나 설치하는 플러그인으로 키운다.

## 1. 의도

Claude Code 생태계는 매주 바뀐다(CLI 판 · 공식 플러그인 · 스킬 · MCP · 하네스 구조 아이디어). 사람이 따라가면 놓치고, 다 들이면 과설계가 된다.
AI-SCOUT 는 **매주 정해진 원천을 훑어 「내 환경에 맞는 것」만 점수로 골라 받은함(GitHub 이슈)에 올리고, 사람이 댓글로 판정하면 다음 주에 장부에 반영한다.** 도입은 언제나 사람이 한다.

첫 사용자는 개인 하네스 하나(지금의 주간 스카우트)이고, 목표는 **사내 개발자가 자기 환경 — 개인 하네스가 있든 없든 — 에 세 줄로 설치해 쓰는 것**이다. 사내 AI 발표에서 운용 결과와 함께 소개한다.

## 2. 목표 · 비목표 · 반목표

| | |
|---|---|
| **목표** | ① 매주 자동: 수집 → 채점 → 이슈 → 사람 판정 → 장부 반영의 한 바퀴 ② 플러그인으로 설치(`/plugin marketplace add` → `/plugin install` → `/ai-scout:setup`) ③ 프로필로 사람마다 맞춤(하네스 있음 · 없음 · 팀) ④ 발표 근거가 운용 중 저절로 쌓인다(주별 수 · 점수 대 판정 · 원천별 수확) |
| **비목표** | 자동 도입(설치 · 설정 변경) · 사전 시험 자동화(사람이 자기 PC 에서) · Claude Code 를 안 쓰는 사람 · 다른 에이전트(Cursor · Codex) 지원 · 팀 모드 — §12 「나중」 |

## 3. 제약 — 실측 (2026-11-09)

| 사실 | 근거 |
|---|---|

| **발표는 4주 안**(12월 초까지) — 4주 주기 장치(문턱 점검 · 원천 정리)는 발표 전에 한 번도 돌지 않을 수 있다. 발표에는 「설계된 다음 단계」로 소개한다 | 사용자 답(11-09) |

## 4. 고른 방식과 버린 것

| 결정 | 고른 것 | 버린 것 · 이유 |
|---|---|---|
| 받은함 | **GitHub 이슈** — 추천이 있는 주만 이슈 1개, 사람은 댓글로 판정 | 브랜치 파일만(볼 곳이 없고 판정 기록이 안 남는다) · PR(추천 대부분이 파일 변경이 아니다 — 11-09 추천 2건 모두 코드 0줄) |
| 알림 | Claude 앱 푸시 = 신호(한 줄 + 이슈 링크). 다시 읽기 · 판정은 이슈 | GitHub 알림(자기 활동이라 안 온다) |
| 설치 | **Claude Code 플러그인** + `/ai-scout:setup` | exe(루틴 생성 · GitHub App 설치를 못 한다 · OS 별 빌드 · 서명 없는 exe 는 사내 보안 프로그램과 부딪힌다) · API 직접 호출 프로그램(API 키 · 종량 과금 · 수집 · 이슈를 다시 만든다) |
| MCP 분리 | **지금은 안 한다** — 수집은 스크립트. 다른 에이전트 사용자가 생기면 스크립트를 MCP 로 감싼다 | 지금 MCP(클라우드에서 쓰려면 호스팅하거나 등록이 필요하다 · 저장소 등록 MCP 가 클라우드에서 도는지 미확인) |
| 엔진 저장소 | **개인 GitHub 공개**(`<owner>/ai-scout`) — 동료가 한 줄로 마켓을 더한다. 엔진에는 사내 정보가 없다 | 회사 GitHub 조직(App 설치에 조직 관리자 승인) |
| 결과 저장소 | 첫 사용자(나)는 **엔진 저장소에 함께 공개**(11-09 사용자 결정) — 프로필에 사내 정보가 없고, 발표 때 실제 예시가 된다 · 동료는 각자 저장소(사내 환경이 적히면 비공개) | 나도 따로 비공개 저장소(저장소 2개 · App 설치 2번) |
| 고르는 법 | **점수 기준(절대평가)** + 후한 문턱, 상한 7 | 상위 5(빈 주에 억지로 채우고, 주끼리 비교가 안 되고, 문턱을 맞출 수 없다) |
| 2단 원천(허용 목록 밖) | **1단 + 웹 검색으로 4주** 운용 뒤 다시 본다 — 동료 기본값과 같은 조건에서 먼저 검증 | 지금 허용 목록에 추가(설정 변경 · 동료마다 설정이 필요) |

## 5. 구조

```
엔진 저장소 <owner>/ai-scout (공개)          결과 저장소 <각자>/ai-scout-<이름> (비공개)
├─ .claude-plugin/marketplace.json           ├─ profile.md        ← 사람마다 (§7)
├─ .claude-plugin/plugin.json                ├─ ledger.md         ← 판정 장부 · 원천 수확 (§10)
├─ SCOUT.md       ← 매주 절차 · 채점 · 형식   ├─ sources.local.json ← 사람마다 더하는 원천 · 고정 플러그인
├─ sources.json   ← 1단 원천과 읽는 길       ├─ reports/YYYY-MM-DD.md · .json ← 보고서 · 이슈 번호와 항목 번호
├─ lib/ · tools/  ← collect(수집 · 비교) · select(합산 · 선택) · judge(판정 줄) — Node 20+, 의존성 0
└─ skills/setup/SKILL.md ← /ai-scout:setup (2단계)   └─ snapshots/ ← 지난주 비교용 (collect 가 쓴다)
```
첫 사용자는 두 쪽을 한 저장소(`<owner>/ai-scout`, 공개)에 둔다 — 결과 파일이 엔진 루트에 함께 있고, 루틴 sources 는 그 저장소 하나다. 엔진은 그래도 같은 저장소의 태그를 `/tmp/ai-scout/` 로 받는다(동료와 같은 길 · main 을 고쳐도 태그를 올리기 전엔 그대로).

결정론으로 할 수 있는 것(수집 · 비교 · 점수 합산 · 문턱 · 상한 · 판정 줄 해석)은 스크립트가, 판단(관련성 채점 · 요약 · 문장)은 Claude 가 한다. HTTP 는 `curl` 로 부른다(클라우드 프록시). 페이지 모양이 바뀌어 0개가 잡히면 실패로 다뤄 스냅숏을 지킨다 — 단 기간 검색(`{since}`) · 고정 점검은 0개가 정상이고, 기간 검색의 스냅숏은 쌓는다.

- **실행 방식**(셋 다 같은 `SCOUT.md` 를 따른다): ① 클라우드 예약 — 기본 ② GitHub Actions — 예약을 못 쓰는 사람 ③ 로컬 `claude -p` — 문서로만 안내
- **클라우드 실행이 엔진을 받는 법**: 루틴 sources 는 결과 저장소 하나(이슈 쓰기가 그 저장소에만 되므로). 실행 첫 단계에서 엔진을 **고정한 태그로** `git clone --depth 1 -b <태그>` 한다 — 엔진이 바뀌어도 사용자가 태그를 올리기 전에는 그대로다. 루틴 지시문은 짧게: 「엔진 <태그> 를 받아 `SCOUT.md` 를 따르라」 + §9 의 금지 사항(문서가 지시문은 자족적이길 권하므로 금지 사항은 지시문에도 둔다)
- 루틴 연결 도구(MCP connector)는 **비운다**(`clear_mcp_connections`) — 웹 글의 숨은 지시가 사용자 계정 서비스에 닿지 않게. 내장 GitHub MCP 는 그대로 있다

## 6. 매주 흐름 — `SCOUT.md`

1. **엔진 · 프로필 · 장부를 읽는다.** 프로필이 하네스 문서를 가리키면 그것도 읽는다(공개면 raw, 결과 저장소 안이면 파일)
2. **지난 판정을 반영한다.** 열린 `[AI-SCOUT]` 이슈의 댓글에서 판정 줄(§8)을 읽어 장부에 적고, 닫을 조건(§8)이 된 이슈는 닫는다. 4주 넘게 아무 판정이 없는 항목은 장부에 「판정 없음」(점수가 오르면 다시 올릴 수 있다)
3. **수집한다** — `node tools/collect.mjs` 가 1단 원천(§9)을 읽어 `snapshots/` 와 비교해 새 항목만 낸다 + 프로필의 「지켜볼 고정 플러그인」을 `git ls-remote` 로 비교 + 프로필의 추가 원천
4. **공식 변경을 전부 요약한다** — 공식 원천의 새 항목은 빠짐없이 한 줄씩(「이번 주 공식 변경」). 공식 새 항목은 모두 5 의 채점 대상(관련 없으면 관련성 0) · 인접 원천은 채점하지 않고 한 줄 요약만
5. **채점한다**(§10) — 먼저 웹 검색으로 커뮤니티 발견을 보충해 후보에 넣는다(select 뒤로 밀리지 않게 이 단계에 둔다). 장부에서 기각 · 도입됨은 건너뛴다(「다시 볼 조건」 충족 시만 재채점). 문턱 이상을 점수순으로, 최대 7개
6. **기록한다** — `reports/YYYY-MM-DD.md` · `ledger.md` · `snapshots/` 를 커밋 · push
7. **추천이 1건 이상이면 이슈를 만든다**(§8). 스카우트는 이슈에 **댓글을 달지 않는다** — 그래서 댓글은 모두 사람의 판정이다
8. **푸시 알림**: `AI-SCOUT 추천 N건 — 이슈 #M <링크>` 한 줄. 0건이면 `AI-SCOUT 0건 (공식 변경 K건) <보고서 링크>`. 둘 다 끝에 ` · 개념 C건`(§10-1)

5 와 따로 **「이번 주 개념」**(§10-1)을 모은다 — 채점 · 판정 밖, 보고서 절과 이슈 본문 목록만.

## 7. 프로필 — `profile.md`

| 절 | 내용 | 하네스 없음 | 하네스 있음 |
|---|---|---|---|
| 나 | OS · 주 언어 · 기술 스택 · 보고 언어 · 관심 개념(§10-1 개념 검색어) | setup 이 PC 에서 읽는다(관심 개념은 묻는다) | 같음 |
| 가진 것 | 플러그인 · 스킬 · MCP · 훅 | setup 이 `~/.claude` · 프로젝트 설정에서 읽는다 | + 하네스 요약 |
| 겪은 문제 | 최대 5줄 — 관련성 점수의 기준 | setup 이 「요즘 불편한 것 3가지」를 묻는다 | 하네스의 보류 · 미해결 목록 **경로**를 가리킨다(복사하지 않는다) |
| 기각 목록 | 다시 올리지 말 것 | 비어 있음 | 하네스의 기각 기록 경로 |
| 지켜볼 고정 플러그인 | 저장소 URL + 고정 커밋 | 선택 | 하네스의 마켓 파일 경로 |
| 추가 원천 | 스택별 원천(예: 쓰는 프레임워크 릴리스) | 선택 | 선택 |
| 문턱 | 기본 5 | | |

- **하네스가 클라우드에서 안 보이면**(비공개 · 회사 저장소 · PC 에만) 「하네스 없음」 갈래로 보낸다 — 겪은 문제는 setup 이 묻는다. 루틴 sources 를 늘리지 않는다(늘리면 그 저장소에도 쓰기가 열린다 · §13)
- **하네스 기록과 장부가 엇갈리면 하네스 기록이 이긴다** — 사람이 직접 고치는 정본이다. 장부는 스카우트가 본 것의 기록
- 「가진 것」은 setup 때 찍은 값이라 낡는다 — setup 을 다시 돌리면 차이를 보여 주고 갱신한다. 하네스가 있으면 「가진 것」이 하네스의 마켓 · 설정 파일을 가리키므로 저절로 최신이다

**첫 사용자 프로필**(옛 스카우트에서 옮긴다)은 「하네스 있음」의 예다 — 하네스의 계획 · 구조 문서와 기각 기록을 가리키고, 고정 플러그인은 하네스의 마켓 파일을 가리킨다. 첫 사용자의 프로필 · 장부는 엔진 저장소에 공개로 있다(사내 정보 없음 — §13 프로필 기본 규칙).

## 8. 이슈 · 판정

```
제목: [AI-SCOUT] 2026-11-16 — 추천 3건 (공식 변경 12건)

1. (9점) 이름 — 무엇 한 줄
   왜 나에게 · 가장 작은 도입 · ⚠️ 보안(있으면) · 출처
2. (7점) …
(처음 2주만) 아깝게 빠진 것: (4점) … · (4점) …

판정은 댓글로 한 줄씩:  1 채택 / 2 기각: 이유 / 3 보류: 다시 볼 조건 / 1 도입
보고서: <reports/2026-11-16.md 링크>
```

- 판정 줄 형식: `<번호> <채택|기각|보류|도입>[: 이유]` — 한 댓글에 여러 줄 가능 · 같은 번호는 마지막 줄이 이긴다 · 형식에 안 맞는 줄은 무시한다
- **채택** = 들이겠다(할 일). 실제 도입(사전 시험 · 설치)은 사람이 자기 PC 에서 한다 — 하네스가 있으면 그 절차대로. 끝나면 같은 이슈에 `1 도입` → 장부 「도입됨」
- 이슈는 모든 항목이 **기각 · 보류 · 도입**이 되면 닫힌다 — 채택이 남은 이슈는 열려 있다(열린 이슈 = 할 일 목록). 4주 동안 아무 판정이 없는 항목만 「판정 없음」으로 정리한다

## 10-1. 개념 칸 — 「이번 주 개념」 (2026-11-09 추가)

- **왜**: 사용자 질문(11-09) 「스카우트가 지식도 알려 주나」. 스카우트는 도구 · 릴리스만 채점해, 새 개념(층 모델 프롬프트 → 컨텍스트 → 하네스 → 루프 → 그래프 · 소프트웨어 팩토리 같은 것)은 웹 검색에 우연히 걸릴 때만 보이고 낮은 점수로 묻혔다. 개념은 설치할 것이 아니라 **우리 구조에 질문을 던지는 것**이다
- **도구 채점과 분리한 이유**: 도입 비용 · 환경 점수가 개념에는 맞지 않는다(설치할 것이 없어 점수가 부풀거나 0 으로 묻힌다). 채택 · 도입 판정도 맞지 않는다. 그래서 문턱 · 상한 · `select.mjs` · 판정 줄 밖에 두고, 이슈에는 번호 없이 목록만 싣는다. 개념 검색 발견은 후보 M · `--expect` 에 세지 않는다
- **후보**: 공식 원천(Anthropic engineering · news · Claude 블로그)의 새 글 + 웹 검색 1~3회 중 1회를 쓰는 개념 검색(프로필 「관심 개념」 낱말) + 그 글이 가리키는 원문. 원문 호스트(논문 사이트 등)가 클라우드 허용 목록에 있는지는 미확인 — 막히면 「원문 미확인」
- **한 줄 형식**: 용어 · 한 줄 정의(원문에서) · 처음 말한 쪽 · 우리 하네스의 어느 층인가(프롬프트 · 컨텍스트 · 하네스 · 루프 · 그래프) · 시사점 · 근거 등급
- **근거 등급**: 원문 2 · 해설 글 1 · 벤더 글 0(⚠️). 11-09 조사에서 이 분야 출처는 블로그 · 벤더 글이 대부분이고 원문은 드물었다 — 등급이 없으면 벤더의 자체 주장이 정의로 굳는다. 벤더 주장은 「자체 주장」으로 적는다
- **주당 최대 3**: 알림이 소음이 되지 않게(§2 반목표). 장부 「개념」 표로 같은 용어가 다시 오르지 않게 하고, 새 원문이 나오면 그 줄만 고친다
- 알림 첫 줄 끝에 ` · 개념 C건`(0 이어도) — 개념 단계가 돈 줄 안다

## 13. 보안

- 스카우트는 **추천만** 한다: 설치 · 설정 · 훅을 바꾸지 않고, `ledger.md` · `reports/` · `snapshots/` 밖에 쓰지 않는다(엔진과 같은 저장소여도 엔진 · 프로필은 읽기만)

- **프로필 기본 규칙**: 내부 시스템 이름 · 프로젝트 이름 · 사람 이름 · 내부 URL 을 적지 않는다 — setup 이 환경을 읽을 때도 이것들은 빼고 일반 이름(언어 · 프레임워크 · 도구)만 남긴다. 회사 정책 확인 전까지의 기본값이다
